# SPEC ドキュメント

機能ごとに `docs/spec/<連番>-<機能名(kebab-case)>/` を作成し、
`requirements.md` → `design.md` → `tasks.md` の順に作成・レビューしてから実装に入る。

## フォルダ命名規則

```
docs/spec/001-user-authentication/
docs/spec/002-chat-history/
```

- 連番 3 桁: 着手順。仕様の依存関係を追いやすくするため。
- 機能名: 英小文字の kebab-case。実装のディレクトリ名 / ブランチ名と揃える。
- ブランチ名は `feat/001-user-authentication` のように spec 名を含める。

## 3 つのドキュメントの役割

| ファイル | 目的 | 答えるべき問い |
| --- | --- | --- |
| `requirements.md` | 要件 | なぜ作るのか / 誰が何をできるようになるのか / 完了条件は何か |
| `design.md` | 設計 | どう作るのか / API・データモデル・画面遷移・エラー処理はどうなるか |
| `tasks.md` | 作業分解 | 何をどの順に実装するか / 各タスクの完了条件は何か |

## 進め方

1. `_template/` をコピーして新しい spec フォルダを作る。
2. `requirements.md` を書き、人間のレビューを受ける。**承認されるまで design には進まない。**
3. `design.md` を書き、レビューを受ける。要件に書かれていない仕様を勝手に足さない。
4. `tasks.md` に分解する。1 タスク = 30〜90 分程度、テストまで含めて完了できる粒度にする。
5. タスクを上から実装する。完了したタスクは `- [x]` にし、設計変更が起きたら `design.md` も更新する。
6. 機能が完了したらルートの `README.md` の機能一覧 / アーキテクチャを更新する。
